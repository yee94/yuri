## 原始研究结论

以下至检查点章节保留最初选型设计，非当前实现清单。实际协议是单条已认证
`/api/gui-network/ws` 内复用最多 32 个 TCP 流，16 KiB 分块、128 KiB/流 credit；
当前使用主 WebView 和独立原生 Relay wire。实现与验收状态以上节及 owning docs 为准。

**首版选择：专用原生 WebView → 手机 loopback SOCKS5 → Yuri 现有加密 Relay 的 WebSocket 子流 → 连接 Host 的 TCP 出口。** Projects 顶部增加应用启动器，图标卡片打开本机执行的 GUI 插件页面；HTML、JS、Solid、布局和交互留在手机，目标站点连接由 Host 建立。此路线保留网站原始 URL、TLS、Cookie 与浏览器跨源规则，避免先实现整套网页重写系统。先交付新版 Capacitor 的 iOS 17+、Android API 28+ 且代理能力可用的设备；普通 H5 和旧系统需要后续承载方案，不能算作已支持。**立即进入 Host 出口、原生容器和入口接线实现；平台探针是首个工程检查点，不是继续泛调研的理由。** 当前证据尚不能支持“任意第三方代码、所有浏览器网络零旁路”的发布承诺，尤其是 WebRTC。

原始选型依据为三份研究笔记及当时源码复核；研究阶段的运行证据只有 Scramjet 的 Node 重写原型。后续已实现产品接线并执行上述构建和原生探针。([集成研究](../research_notes/移动插件本地渲染与中继代理/integration.md)) ([原生研究](../research_notes/移动插件本地渲染与中继代理/native.md)) ([代理库研究](../research_notes/移动插件本地渲染与中继代理/proxy.md))

## 原生 TCP 代理是首版最小主线，许可证也最贴合现有项目

原生代理在浏览器网络层接收 HTTP(S)/WS(S) 连接，因而不需要逐项重写 iframe、CSS、动态 script、fetch、XHR 或 WebSocket。嵌套第三方文档也沿用同一浏览器网络配置，HTTPS 的 TLS 握手与证书校验仍发生在手机 WebView；Host 只连接目标并搬运 TCP 字节。Chromium 明确支持 SOCKSv5 的代理端域名解析，但只承载 TCP；WebKit 有公开代理配置，WS 的实现也使用相应网络 session。**这些是选择该路线的依据，不是已在 Yuri 手机上验证过的结果。**([Chromium 代理机制](https://chromium.googlesource.com/chromium/src/+/HEAD/net/docs/proxy.md)) ([Apple 代理配置](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/proxyconfigurations-cdc1)) ([WebKit 网络实现](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/NetworkProcess/cocoa/NetworkSessionCocoa.mm))

| 方案 | 已核实条件 | 本次决策 |
|---|---|---|
| 原生代理＋Yuri TCP bridge | 使用系统 WebKit、AndroidX WebKit、现有 Relay；不用网页重写依赖 | **选为首版。** SOCKS5 只实现 CONNECT；拒绝 UDP ASSOCIATE。Android app 显式声明所用 AndroidX WebKit 依赖，优先沿用仓库版本 |
| Hammerhead 31.7.9 | MIT；完整 Node 代理使用两个监听端口及根路径代理 URL，没有一等 basePath 传输适配 | 许可证合适，但还要双 origin 网关和页面改写，不是当前原生首版的最小实现 |
| Ultraviolet 3.2.10 | MIT；官方说明不再积极维护；实现依赖 SW/browser 上下文 | 不选为新增核心依赖 |
| Scramjet 2.0.67-alpha.2 | AGPL-3.0-only；core 可注入 HTTP/WS transport；已验证无 SW 的 Node handler，但未验证手机执行 | 保留为 H5/旧系统后续候选，不进入本次原生主线 |

版本、维护状态和接口依据分别见官方仓库及发布包。Scramjet 的 `latest=1.1.0` 与 2.x alpha 接口不同，且 1.1.0 npm 授权字段与包内 LICENSE 存在冲突，不能作为“MIT 版本”直接采用。([Hammerhead](https://github.com/DevExpress/testcafe-hammerhead)) ([Ultraviolet](https://github.com/titaniumnetwork-dev/Ultraviolet)) ([Scramjet 固定版本元数据](https://registry.npmjs.org/@mercuryworkshop/scramjet/2.0.67-alpha.2)) ([发布包核验记录](../research_notes/移动插件本地渲染与中继代理/proxy.md))

Yuri 当前是 **MIT**，Capacitor 8.4.1 是 MIT，AndroidX `ProxyController` 源文件是 Apache-2.0；首选路线无需引入新的强 copyleft 网页引擎，保留相关版权、许可证及适用 NOTICE 即可按各自条款集成。AGPL 并非禁止商业用途，也不意味着 MIT 代码不能参与组合；但把 Scramjet 捆绑到客户端或用于服务，会增加须按实际组合、修改与分发方式落实的源码提供等义务，不能把最终组合仍当成只有 MIT 义务。用户允许加依赖不等于这些义务消失，这也是本次不以它作为最低成本首选的原因。([Yuri LICENSE](../LICENSE)) ([Capacitor 元数据](https://registry.npmjs.org/@capacitor/core/8.4.1)) ([AndroidX 许可证及 API](https://github.com/androidx/androidx/blob/androidx-main/webkit/webkit/src/main/java/androidx/webkit/ProxyController.java)) ([Scramjet LICENSE](https://github.com/MercuryWorkshop/scramjet/blob/main/LICENSE))

## 新增 Host TCP 出口，保持现有 Relay 的加密与转发职责

```text
手机专用 GUI WebView：本地 bundle / Solid / DOM / 第三方 iframe
  → WebKit/Chromium 代理配置
  → 127.0.0.1:临时端口 SOCKS5 gateway
  → 有界 native IPC：目标地址、字节、credit、FIN/RESET
  → 主应用持有的、绑定当前 Host 的 Relay tunnel
  → 既有 WsBinary / WsText，加密后经既有公网 Relay
  → Host 本机 /api/gui-network/tcp/ws
  → Host DNS + TCP connect
  → 目标 HTTP(S)/WS(S) 服务器
```

**新增的是 Host 领域出口，不是另一个 Relay 服务。** 当前 dispatcher 只把允许的 HTTP/WS 路径送到 Host 自身 Yuri 服务的 loopback 端口；直接给 `runtimeFetch` 一个第三方绝对 URL 会走设备网络，把外部 URL 交给 runtime socket 也不会让 Host 拨到该域名。因此新增 `server/lib/gui-network/`，由其拥有 lease、目标校验、DNS、TCP、流控与清理；dispatcher 仍只访问本机 Yuri API。现有加密握手、wire frame、配对信任锚及 Layer 1 relay-server 均可沿用。([Relay 分层与边界](../packages/web/server/lib/relay/DOCUMENTATION.md)) ([现有 HTTP 分流](../packages/ui/src/lib/runtime-fetch.ts)) ([Host WS dispatcher](../packages/web/server/lib/relay/tunnel-host.js#L347))

**首版内部协议固定为“一条 TCP 连接对应一条现有 WS 子流”。** 经认证的 HTTP API 创建容器 lease；通过现有 URL-scoped token 授权 `/api/gui-network/tcp/ws`，首帧提交 `v/leaseId/hostname/port`，Host 校验并连接后返回 `opened`，手机才答复 SOCKS success。二进制帧承载原始字节，控制帧提供 `credit/fin/reset`；TCP 半关闭必须独立表达，不能用 WS close 代替。域名和 IP literal 都交 Host，手机 gateway 不自行解析目标或拨外网；目标端口及私网访问策略由 Host lease 明确定义，Host 上允许的 localhost 指 Host 自身。Yuri 授权只用于外层 API，不注入网站流量。上述路径和消息是本报告建议的新契约。

新 WS 路径必须同时加入 `tunnel-host` 和 `ui-auth` 的精确 allowlist。当前 `handleWsOpen` 不转发调用者的任意 headers，不能依赖传入 Authorization header 解决鉴权。两端 sender 都要把该路径加入已有 immediate-flush 条件，否则现有 **150ms batch window** 会放大 TLS 握手和页面多轮请求延迟；只改单端不能消除双向等待。([鉴权契约](../packages/web/server/lib/relay/DOCUMENTATION.md#authentication-model)) ([Host headers 与 flush](../packages/web/server/lib/relay/tunnel-host.js#L374)) ([Client flush](../packages/ui/src/lib/relay/tunnel-client.ts#L858))

流控从第一版就实现：建议初始值为每块不超过 32KiB、每流未确认数据不超过 256KiB、单容器总队列不超过 4MiB、并发 TCP 不超过 32；这些是待压测调整的设计值。credit 只能在下一跳实际消费后归还，并覆盖 Native↔JS↔Relay↔Host TCP 两个方向；控制消息、超时和超限同样有界。现有 `send()` 返回 void，不能当作已经具备完整背压。压力测试需检查大页面不会饿死现有聊天/SSE。([当前 Relay socket 接口](../packages/ui/src/lib/relay/tunnel-client.ts#L95))

**强制 Relay 必须成为连接 owner 的能力，不能靠组件检查一次布尔值。** 已处于同一 Host/Relay 时复用 active tunnel；主应用在 LAN 模式时，由 runtime owner 用已保存且验明身份的 Relay candidate 申请引用计数 lease，仍使用同一客户端实现和既有 Relay 服务，不让视图组件切换全局实例。没有有效 candidate、Host 出口能力或活连接就失败；不用会自动落到 direct 的 helper 兜底。lease 绑定 `runtimeKey + relayUrl/serverId + transport generation + containerId/epoch`，所有异步回包再次核对，处理 A→B→A 与 LAN↔Relay 切换。([active tunnel 所有权](../packages/ui/src/lib/relay/runtime-tunnel.ts)) ([候选与身份校验](../packages/web/server/lib/relay/DOCUMENTATION.md#candidate-refresh-staying-off-the-relay-when-direct-works))

## Projects 入口复用手机导航，插件执行必须完整迁入受控容器

Projects 的 `MobileProjectsHome` 已提供标题 trailing 区域，直接增加一个应用启动器按钮；其叶子组件订阅 GUI 页面快照，不把插件数据塞进会话目录模型。启动器展示已启用且真实注册的 `yuri.page` 图标卡片，以 `[pluginId,pageId]` 元组定位页面；一插件有多个页面就显示多张页面卡片，首版不猜“默认主页”。图标沿用现有 IconName/alias/fallback；目前页面契约没有 package artwork 或 page 与 TitlebarItem 的关联。([Projects 接点](../packages/ui/src/mobile/projects/MobileProjectsHome.tsx#L549)) ([页面契约](../packages/ui/src/lib/gui-plugins/pages.ts)) ([现有图标实现](../packages/ui/src/components/gui-plugins/GuiPluginTitlebarItems.tsx))

导航增加 launcher 状态和可选 `activePageKey`：**Projects → 应用卡片页 depth 1 → 插件页 depth 2**，沿用 `MobilePhoneShell`、`MobileTabsRoot` 的返回、手势、焦点恢复、safe area 和 dock 隐藏。当前公共移动标题已经散列展示 TitlebarItem；新入口接入时要处理重复展示，但不得按名称猜测 action 对应哪个页面，或删掉没有页面关联的有效动作。手机选择状态归 mobile store，`pages.current/open` 注入手机导航；用承载 capability 替换现有 narrow 禁用条件，而不是接桌面 `activeGuiPage`。([现有公共标题](../packages/ui/src/mobile/MobileTabPageHeader.tsx#L106)) ([手机导航模型](../packages/ui/src/mobile/mobileNavigation.ts)) ([二级页承载](../packages/ui/src/mobile/MobileTabsRoot.tsx))

**不能只在现有 Solid DOM 外面套一个 WebView。** 当前插件 CJS 在主文档 `new Function` 求值，`setup/render` 闭包、Style、网络与 SDK 都属于那个 realm。首版应抽出本地 `gui-plugin.html` bootstrap，在受控原生容器内复用同份 `host/bundle/SDK/Solid`，每个实例只执行一次 setup；主应用通过窄接口接收序列化贡献快照、发送动作与挂载请求，并提供当前 session、files、主题、locale 和受限 SDK RPC。options 留在所属插件内存，不进入快照、URL 或持久缓存；外部 iframe 不获得主 Capacitor bridge 或 Relay 密钥。([求值边界](../packages/ui/src/lib/gui-plugins/bundle.ts)) ([当前 host 职责](../packages/ui/src/lib/gui-plugins/DOCUMENTATION.md#所有权与运行时)) ([当前具体 host 类型依赖](../packages/ui/src/lib/gui-plugins/react.ts))

最小 owner 选择是**每个当前 runtime 一个专用 GUI 容器，共用一个窗口 host**，保留已有跨插件 Registry/Contract 语义。移动端主 Provider 改为该 host 的代理，不再在主文档重复 setup；原有 panel/settings/文件预览必须投影到同一容器能力，否则同一插件仍有未受控执行路径。原生层负责展示区域与销毁，手机 React 层负责导航和外壳。关闭一个页面调用其 mount disposer，不能等同于停用插件；切 Host、容器销毁、Relay generation 失效则撤销整套网络 lease。**SOCKS 握手不包含 pageId/pluginId，首版只能可靠按容器归属连接，不能假称具有每插件 TCP 精确审计。** 若必须硬取消某页全部浏览器连接，使用容器级网络 epoch 重置，并验证其他贡献的恢复行为。

这是主要集成工作量，应在实现检查点明确解决；“parent 先 setup 发现页面，点击后 native 再 setup 一遍”会重复监听并留下直连窗口，不能作为首版捷径。原生入口可随现有 web dist 一起打包，mobile 的资产准备脚本已经复制整套 web dist，无需再复制第二套完整 UI。([插件生命周期](../packages/ui/src/lib/gui-plugins/host.ts)) ([资产复制](../packages/mobile/scripts/prepare-web-assets.mjs))

## 平台能力限定首发覆盖，代理配置不等于全网隔离

| 环境 | 首版承载与初始化 | 必须验证的边界 |
|---|---|---|
| iOS/iPadOS 17+ | 专用 WKWebView 和独立 nonpersistent `WKWebsiteDataStore`；先 bind SOCKS、配置 `proxyConfigurations`，显式 `allowFailover=false`，再加载任何插件代码 | SOCKS 是否传域名、localhost/IPv6/link-local 是否绕过、WS/WSS、旧系统具体行为；iPad 页面入口另接其布局分支 |
| Android API 28+ 且 `PROXY_OVERRIDE` 可用 | 独立 `:gui` 进程；任何 WebView 初始化前设置 data-directory suffix；配置单一 SOCKS rule、`removeImplicitRules()`，等待 callback 后加载 | 代理是进程级；不加入 DIRECT/bypass。数据目录按 runtime 分区，切 Host 重启相应容器进程；独立进程本身不提供网络沙箱 |
| iOS 15.5–16、Android 24–27、旧 native shell | 首版不运行需要该代理能力的页面，明确说明所缺系统/壳能力 | 保留 app 当前最低系统版本，不把库升级误当成系统 API 升级 |
| Hosted mobile / 普通浏览器 | 首版不可用原生代理 | H5 必须另做受控 renderer origin、SW 资源入口和自定义 Relay transport；不能静默打开原始外链冒充同等支持 |

最低版本、配置时序和作用域来自平台公开 API；当前项目 iOS target 仍是 15.5、Android minSdk 24。Apple data-store 代理不是单 iframe 配置；Android `ProxyController` 更不是 per-WebView 配置。专用容器使主应用的 Relay 承载 WS 不被递归吸入 SOCKS，并避免修改整个主 WebView 的联网行为。([Apple API](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/proxyconfigurations-cdc1)) ([Apple failover](https://developer.apple.com/documentation/network/proxyconfiguration/allowfailover)) ([Android 进程级代理](https://github.com/androidx/androidx/blob/androidx-main/webkit/webkit/src/main/java/androidx/webkit/ProxyController.java)) ([Android bypass](https://developer.android.com/reference/androidx/webkit/ProxyConfig.Builder#removeImplicitRules())) ([数据目录 API](https://developer.android.com/reference/android/webkit/WebView#setDataDirectorySuffix(java.lang.String))) ([当前 iOS 配置](../packages/mobile/ios/App/Podfile)) ([当前 Android 配置](../packages/mobile/android/variables.gradle))

**用户列出的 iframe、资源、script、fetch/XHR、WebSocket 属于本次必须完成的 HTTP(S)/WS(S) 验收面；“任意网络 API 均不能绕过”是另一个尚未解决的严格能力。** WebRTC 存在独立 DNS、UDP/TCP 路径；公开 WKPreferences 没有已核实的完整关闭开关，AndroidX 也未核实能设置 Chromium 的完整 RTC 网络策略。删除 JS API、拒绝摄像头权限或添加 CSP 不能据此证明所有 realm/worker 都被封锁。WebTransport/QUIC、DNS 预取、共享/服务 worker、下载和外部浏览器入口同样需要明确测试或拒绝路径；不能将“未支持”标签当作真正阻断。([WebKit RTC resolver](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/NetworkProcess/webrtc/NetworkRTCProvider.cpp)) ([WebKit RTC TCP](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/NetworkProcess/webrtc/NetworkRTCTCPSocketCocoa.mm)) ([公开 WKPreferences](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKPreferences.h)) ([AndroidX WebSettingsCompat](https://github.com/androidx/androidx/blob/androidx-main/webkit/webkit/src/main/java/androidx/webkit/WebSettingsCompat.java))

能力状态应分别记录 `tcpProxyAvailable` 和 `strictNetworkIsolationAvailable`。后者没有证据就为 false，不能把本次首版表述成任意不可信网页零旁路沙箱；如果验收坚持这个字面要求，**严格模式对未通过隔离条件的容器必须拒绝执行，该部分是实际交付阻塞项**。它不阻止立即编写和测试 TCP 链路、容器与应用启动器，也不能用“先发可信插件”偷换完整验收。保留原生跨源规则意味着 CSP、X-Frame-Options、混合内容、第三方 Cookie、设备绑定登录仍可能限制具体站点；网络走 Host 不会自动解除这些限制。([严格能力研究边界](../research_notes/移动插件本地渲染与中继代理/native.md))

## 按五个检查点推进代码，完成标准是手机网络证据

以下为最初规划的检查点；部分代码和验证已完成，具体进展以上方实现状态为准。

端到端 fixture 使用真实 CJS/Solid 页面与 A→B→C 嵌套跨源 iframe，覆盖 CSS import/字体/图片、动态 script/import、GET/HEAD/POST/PUT/PATCH/DELETE、JSON/multipart/二进制上传、302/307、Cookie/HttpOnly、Range、SSE 首事件、WS 文本/二进制/subprotocol/关闭以及正确和错误 `postMessage targetOrigin`。同时验证 localhost、IPv6、blob/srcdoc、新 worker、页面关闭、插件替换、断网、后台恢复、Host 切换和 A→B→A。**目标服务器与权威 DNS 记录应显示请求来自 Host；手机抓包检查目标站点连接和 DNS 是否泄漏。** 再让手机测试网络只放行 loopback 与既有 Relay，确认功能仍工作；该网络限制只能辅助证明功能路径，不能反过来冒充应用自身已经阻断所有旁路。

## 结论

Projects 卡片、本地 GUI 页面和现有 Relay 的 TCP 出口已接通，双端原生构建通过；
**原生代理路线仍未满足全部请求经 Host 的要求**。下一步先在可连接的 iPhone 上
复核最小不可达代理对照，区分模拟器与真机行为。若真机同样旁路，就需要更换网络
拦截机制，不能通过调整代理安装时机或换 data store 宣称修复。独立插件容器、
启动失败回滚/原生销毁的运行验证、Android 网络和完整产品 UI 验收仍待完成。

最终是否达到完整诉求，取决于三项可观察结果：列举的所有网页请求确实从 Host 出网，GUI 只在受控手机容器执行一次，以及“全部网络”的严格边界有真实平台证据。普通 H5/旧系统覆盖与任意代码零旁路仍是明确未解决项，不能通过入口可点击或页面能显示将其计作完成。
