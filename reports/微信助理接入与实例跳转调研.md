# 微信助理接入与实例跳转调研

调研日期：2026-11-03。最终范围仅为用户截图中的「微信助理」，不包含企业微信、QQ、微信客服号。用户要求不再使用子代理后，以下关键官方文档、外部源码与 Yuri 跳转代码均由主代理直接重新读取。未扫码、未调用业务收发接口、未做真机跳转；没有修改产品源码或安装依赖。

## 结论

Yuri 可以实现同类微信助理收发能力，复用自己的 Bot、历史、工具和工作委派管线，不必运行完整 OpenClaw 或让 WorkBuddy 模型转述。可靠做法是复用腾讯公开的 iLink 通道实现，给 Yuri 独立扫码授权，而不是读取 WorkBuddy 已绑定的 token。

但要区分三件事：代码允许复用、微信服务允许某个部署使用、手机端实际验证通过。当前只对第一件事有充分公开证据；独立产品商用准入、扫码账号开放范围和实机链路仍需确认。

内置卡片不能原样渲染成微信交互组件。可先转换成文字摘要加 HTTPS 详情链接；复杂交互留在 Yuri。微信官方支持通过网页按钮唤起 App，并用 `extinfo` 传递自定义目标，但这需要额外资质、原生 SDK 和实例定位流程，不是给现有 `yuri://` 加参数就完成。

## 微信助理的依据与边界

- [WorkBuddy 官方接入指南](https://www.workbuddy.cn/docs/workbuddy/Assistant-Guide#微信助理接入指南)独立列出微信助理和微信客服号；微信助理扫码绑定，要求桌面端常驻。文档描述文字、图片、文件、语音转文字、任务接续和操作确认。
- [官方更新日志](https://www.workbuddy.cn/docs/workbuddy/Changelog)在 4.6.4（2026-03-22）记录微信 ClawBot 集成；与当前微信助理指南的最低版本一致。这是产品对应关系的证据，但没有 WorkBuddy 官方源码或抓包证明截图按钮的全部 endpoint、appid、权限配置与公开插件完全相同。
- [Tencent/openclaw-weixin](https://github.com/Tencent/openclaw-weixin)及其[协议](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol.md)提供二维码授权、bot token、`getupdates` 长轮询、`sendmessage` 回复、图片/文件/视频 CDN 传输及 typing 状态。通常只需 Host 出站 HTTPS，不必部署收消息 webhook。
- [MIT 许可证](https://github.com/Tencent/openclaw-weixin/blob/main/LICENSE)允许源码复用。整包是 OpenClaw 插件，不是直接可装进 Yuri 的独立 SDK；适合移植低层协议，不复制 Agent 层。
- 官方 [channel.ts](https://github.com/Tencent/openclaw-weixin/blob/main/src/channel.ts)声明 direct 私聊、媒体和 blockStreaming；[消息类型](https://github.com/Tencent/openclaw-weixin/blob/main/src/api/types.ts)包括文字、图片、语音、文件、视频、工具起止进度，没有任意自定义卡片、按钮动作或通用点击回调的公开类型。工具进度类型不能等同自定义交互卡片。
- WorkBuddy 日志记录 Markdown 渲染；官方插件[过滤器](https://github.com/Tencent/openclaw-weixin/blob/main/src/messaging/markdown-filter.ts)也保留部分 Markdown。这不证明所有 Markdown 链接、协议链接和客户端版本均可点击，需真机验证；首版建议明确提供 HTTPS 原始 URL。
- 回复应保存并回传入站 `context_token`。不能承诺无限主动推送、固定时间窗、群聊或送达必达；当前协议文档明确不是完整服务端契约。

### GitHub 中容易混淆的方案

[HenryXiaoYang/wechat-openclaw-channel](https://github.com/HenryXiaoYang/wechat-openclaw-channel)的 WorkBuddy 模式明确自述逆向，实际 [codebuddy-api.ts](https://github.com/HenryXiaoYang/wechat-openclaw-channel/blob/main/auth/codebuddy-api.ts)使用 CodeBuddy OAuth、`wechatkfProxy` 与私有 workspace 注册接口。不能用它证明微信助理拥有公共稳定第三方 API，也不建议 Yuri 冒用 WorkBuddy 客户端身份。

[dd814/codex-workbuddy-wechat-bridge](https://github.com/dd814/codex-workbuddy-wechat-bridge)则是 WorkBuddy 调本地 MCP 后转发 Codex，README 明确不直接登录微信，且 WorkBuddy 模型可能改写输入。此路线只能间接桥接，不符合「Yuri 助理直接收发」的优先目标。

## 卡片跳转的可实现程度

| 目标 | 判断 |
| --- | --- |
| 微信文字请求 → Yuri Bot → 回复微信 | 有公开协议和本地执行入口，适合优先 PoC；尚未实机接通 |
| 图片/文件收发 | 有协议与代码依据，需附件适配与安全边界 |
| 微信展示原样 Yuri 卡片并直接点击按钮 | 当前公开协议没有足够依据，不能承诺 |
| 卡片转为标题、状态、摘要、HTTPS 详情链接 | 可设计实现；微信端链接识别、域名访问和风控需实测 |
| 微信内点 `yuri://…` 直接稳定唤起 | 不能保证，不应作为唯一入口 |
| HTTPS 落地页 → 官方「打开 Yuri」按钮 → 指定实例与会话 | 官方支持传参；满足资质并补齐原生及路由能力后可实现 |
| 微信发消息直接唤醒已关机/休眠的 Host | 不支持；通道不代替常驻 Host |

### 微信官方跳转路径

根据[开放标签文档](https://developers.weixin.qq.com/doc/service/guide/h5/opentag.html)与[网页跳转 App 配置规则](https://developers.weixin.qq.com/doc/oplatform/Mobile_App/WeChat_H5_Launch_APP.html)：

1. 微信消息发送 HTTPS 链接，用户打开落地页。
2. 落地页使用 `wx-open-launch-app`，用户点击按钮并确认打开 App。不是聊天里直接运行 HTML 标签，也不是自动无感唤起。
3. `appid` 指向微信开放平台登记的移动应用，`extinfo` 为 App 自行解析的定位信息。
4. App 通过 OpenSDK 接收该信息，再切换已授权 Yuri 实例，待连接就绪后打开 Bot、会话或任务。

必要条件：已认证服务号、已认证且同主体的微信开放平台账号、审核通过的移动应用、服务号 JS 安全域名与 App 的明确关联、网页 JS-SDK 签名验证。Android/鸿蒙唤起要求接入 OpenSDK；获取 `extinfo` 的 App 侧流程也要求接入 OpenSDK。不能把普通 iOS Universal Links 或 Android App Links 的系统能力当成微信内必然放行的证明。

这里使用服务号资质仅为网页唤起能力，**不代表改用微信客服号接收消息**；消息收发仍是本次关注的微信助理通道。

建议 `extinfo`/扩展 deeplink 包含版本、稳定实例身份、资源类型与资源 ID，或可解析的导航引用；不要使用手机本地随机 connection ID 作为跨设备身份，也不要携带 bearer token、微信 token、配对密钥或执行命令。导航不是授权；目标资源仍须按已有身份校验。仅用于导航的链接被微信预取时不得触发审批或任务执行。

## Yuri 已有能力与缺口

### 可复用

- `packages/web/server/lib/assistants/service.js:3369-3416`：`send(assistantID, input)` 已校验、持久化和按 messageID 幂等接收用户输入，进入现有 contact 执行管线。
- `packages/web/server/lib/assistants/service.js:3647-3669`：回复与卡片先持久化，随后发布完成事件，可作为外部出站适配的基础；当前通知仅取最后一条文字，不可直接当完整回复。
- `packages/ui/src/apps/deepLinks.ts:35-45,100-114`：已有 session、assistant 等 intent 与 `yuri://session/<id>`、`yuri://assistant/<id>`。
- `packages/ui/src/apps/deepLinkNavigation.ts:151-165,214-255`：已有冷启动/未连接时暂存导航、连接就绪后执行的机制。
- `packages/ui/src/apps/mobileConnections.ts:189-243`：已有实例连接身份；relay 身份为 serverId 加 relayUrl，直连按规范化 URL 匹配，不以机器名判断实例。
- `packages/ui/src/apps/mobileConnections.ts:1040-1057`：已有按保存的连接 key 安全取凭据、探测并切换实例的原生分享入口；可下沉复用连接逻辑，不应将分享专用入口机械变成所有 deeplink 的 API。
- 卡片目标明确：`AssistantSessionCard.tsx:87-96` 打开工作会话；`AssistantAssistantCard.tsx:31-37` 打开 Bot；`AssistantScheduleCard.tsx:25-27` 按 projectID/taskID 打开任务。路径均在 `packages/ui/src/components/assistants/` 下。

### 必须补齐

- 微信通道：独立扫码绑定、私有凭据、账号/用户→Bot 映射、入站去重、重连、可靠出站及后台结果路由。首版限制本人绑定专用 Bot，避免多联系人共用历史。
- 扩展跳转：当前 session/assistant intent **不含实例身份**，不能正确打开另一台 Host 的内容；当前冷启动默认连接最近实例（`mobileConnections.ts:1014-1035`）。需先定位/认证目标实例，再消费资源导航；缺失或失效时要求配对，不能静默打开当前实例同名资源。
- 任务跳转：网页有 `/schedule/tasks/<projectId>/<taskId>`，但当前自定义 scheme 词汇没有对应 task intent，应统一补充而非另造微信专用路由。
- 原生接入：`packages/mobile/ios/App/App/Info.plist:50-63` 与 Android `AndroidManifest.xml:31-38` 仅注册自定义 scheme；iOS `App.entitlements` 没有 Associated Domains，Android 没有 HTTPS App Links filter。对 mobile 目录检索未发现微信 OpenSDK、WXApi 或 WXEntryActivity 接入。官方唤起流程涉及原生代码/配置和新安装包，不能只靠 OTA。
- HTTPS 落地页与域名关联：链接可指向公共静态导航页，Host 不必因此公网暴露；App 仍通过已配对的直连或 relay 连接 Host。微信内直接打开完整 Yuri Web UI 则另外需要可达地址与有效认证，不能把 relay 的存在等同于任意网页自动可访问。
- 生命周期可靠性：`assistants/DOCUMENTATION.md:24-34` 明确 Host 重启不恢复内存 turn；微信出站重试不等于可以重放整次工具执行。

## 推荐落地次序

先做本人扫码 → 一个专用 Yuri Bot → 微信文字往返闭环，检查业务返回码并由手机确认可见；再加卡片摘要及 HTTPS 链接。之后按实际主体资质选择官方 App 唤起或外部浏览器兜底，补齐实例感知 deeplink。未获得资质时，不承诺微信内一键直达 App；可以保留网页查看、复制链接及外部浏览器打开的替代入口，但这些也需客户端验证。

验收必须覆盖：iOS/Android、App 冷启动/后台、当前连接实例 A 但链接指向 B、未配对/凭据失效、Host 离线、微信域名拦截、卡片仅含链接、长任务后回信、过期 context 和重复消息。以上均尚未实测。
