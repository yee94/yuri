# Remote desktop

## Ownership and supported runtimes

- `runtime.js` owns the authenticated `/api/remote-desktop/ws` session and `/api/remote-desktop` capability response. The routes are installed before the OpenCode proxy/SPA fallback.
- Electron injects a process-local adapter from `packages/electron/remote-desktop.mjs`. Only that Electron Host's physical primary display is captured, irrespective of which OpenCode/runtime the desktop window currently shows.
- The first native input adapter is macOS (Quartz events, Screen Recording and Accessibility consent). CLI/headless, Windows and Linux Hosts return `supported: false`, and WS upgrade returns 501. VS Code explicitly returns 501 rather than proxying these routes to OpenCode.
- Hosted mobile and Capacitor iOS/Android use the same receiving browser UI. No native WebRTC plugin, new dependency, separate desktop server, or OpenCode changes are required.

## Authorization and lifetime

Remote desktop is opt-in. The native-only approval store also owns an `enabled` Boolean that defaults false when missing or malformed; pre-existing device approvals do not imply the feature is enabled. `/api/remote-desktop` exposes `{ supported, enabled }`, and WS upgrades are rejected with 403 while disabled, before starting native consent or capture. The native adapter checks the preference independently. Only local main-frame desktop IPC can inspect setup permissions, change the switch, or request a fixed macOS permission pane. There is no HTTP endpoint to enable it remotely.

The local desktop Settings → Remote instances → Remote desktop group checks Screen Recording, Accessibility for the app and the actual helper executable, and helper installation. The helper's check-only mode posts no input events. Enabling requires all checks to pass and a successful atomic preference write. Closing the switch immediately ends active and pending native sessions. Failed disable persistence leaves the current app run blocked rather than restoring remote access; a restart may still load the old persisted preference, so the failure is visible and must be retried. Preferences and device IDs share the existing serialized native store without replacing each other. UI permission reads use Query, mutations refresh only their native setup/capability keys, stale runtime completions are rejected, and read failures preserve the last snapshot with explicit error feedback. Non-desktop and remote-runtime Settings cannot change local macOS grants. Unsupported desktop platforms show an unsupported state.

The WebSocket must authenticate a paired client or a real password-protected owner session. Password-less/forged owner cookies, loopback source, and raw bearer credentials in query parameters do not qualify. Browser sockets use the existing scoped `yuri_url_token`; the Host checks origin even when password auth is disabled. Both tunnel and URL-token allowlists include exactly `/api/remote-desktop/ws`. Desktop realtime proxying also permits this exact path. No Relay wire-frame types or crypto format change.

The first native session requires local confirmation on the Mac. The unchecked-by-default “Always allow this device” checkbox can persist approval for that authenticated client ID only, so later connections work unattended. Other devices and owner-cookie sessions still require confirmation. A dedicated Electron-owned `remote-desktop-approvals.json` stores at most 256 public client IDs, never tokens, in native userData; missing/malformed data does not authorize a device. Adding a new approval evicts the oldest when full, requiring that device to re-confirm. Writes reuse the serialized atomic settings store; failed writes close capture without claiming the approval was saved. The native sharing window can Stop or Forget device; Forget stops immediately and removes its approval. If removal fails, native error feedback directs the owner to revoke pairing. Remote client revocation remains authoritative and also prevents remembered approval from granting access.

There is one active or pending capture per Host. Closing the native sharing window also stops capture. Stopping the Host, closing the remote view/socket, backgrounding the phone, removing/changing a display, or a native failure stops the session. Client pings are every 5 seconds; 20 seconds without a ping ends the Host session. Active client revocation is checked every 5 seconds, failing closed on store failure. Maximum session length is one hour. Initial client startup has a 60-second deadline, capability requests a 10-second deadline, and native capture startup a 15-second deadline after the local approval.

Runtime generation/transport identity are captured when opening the view. No input or delayed auth result can connect to a different Host. Failure is not an empty success. Reconnection is explicit, not an unattended loop that repeatedly opens native permission dialogs. Closing a pending session aborts the local approval; a later startup completion is immediately disposed. EOF on the helper's pipe releases a held mouse button.

## Media and control

The isolated file-origin capture window uses Electron's `desktopCapturer` screen identity and Chromium's desktop `getUserMedia`, constrained to 1920×1080 and 30 fps. Chromium owns negotiated video codec and hardware acceleration; H.264 is not forced. A WebRTC offer/answer and trickle ICE pass over the authenticated WS. Media uses WebRTC DTLS-SRTP. Over Relay, the fingerprint-bearing signaling and control are also protected by the existing E2EE tunnel; media does not use Yuri's tunnel encryption format.

`YURI_REMOTE_DESKTOP_ICE_SERVERS` optionally supplies an RTCIceServer JSON array (maximum 8 entries). It is configured on the Desktop Host, not the Relay, and passed to both peers for that session. No external STUN service is contacted by default. Deployment-managed TURN credentials are visible to the paired receiving client as necessary for WebRTC and are never persisted or logged by this feature. Prefer short-lived credentials. A TURN credential minting service is not included.

If WebRTC fails, is unavailable, or produces no decoded video within 7 seconds of the answer, the client requests JPEG fallback through the existing runtime WS. This works over Relay without TURN. Fallback is at most 1440×900, JPEG quality 0.65, maximum 512 KiB per frame, and at most approximately 12 frames/second. Only one frame is outstanding: the receiver ACKs after image decode, and capture skips work until ACK. Thus effective frame rate also depends on RTT/encode/decode time; this is not a 30-fps WAN guarantee. WS buffering is capped at 512 KiB. The video fallback shares the connection with other Relay traffic.

The UI calls JPEG fallback “Compatibility stream”, not “Encrypted tunnel”: direct `ws://` transport is not E2EE. Use HTTPS/WSS for direct network connections and TLS for public Relay ingress. JPEG carried through Relay benefits from the existing endpoint-to-endpoint encrypted tunnel; a plain direct LAN connection does not acquire that property merely by using this feature.

Control always stays on the authenticated WS, including when video is P2P. `protocol.js` bounds and projects pointer coordinates, scroll deltas, text (1024 UTF-16 code units), key names, SDP (64 KiB), and ICE candidate fields. There is no arbitrary shell/keycode/file/clipboard API. WS messages are capped at 96 KiB; input is serialized with at most 32 queued commands and 150 messages/second. The native helper checks permission and active display again, and accepts only its own bounded JSON command vocabulary.

## Mobile interaction and performance

The Projects homepage plus menu ends with a Remote desktop icon/action after instance choices. The chat header overflow menu exposes the same action. `MobileApp` owns one open state, one shared handler and one `RemoteDesktopPanel`; the homepage receives that handler through `MobilePhoneShell` and its Projects container. Opening from chat closes the overflow menu without changing the chat/session route. Android Back dismisses the remote desktop before underlying navigation, and underlying root/header swipe navigation is blocked while it is open. The panel uses the current runtime, not a separately selected machine. Tap clicks, double tap is delivered as native double-click, drag moves a held mouse, and long press right-clicks. Scroll mode turns single-finger movement into scrolling. Two fingers zoom (1–5×) around their midpoint and pan the local viewport without sending mouse input. Switching from dragging to pinching releases the mouse; lifting one finger after pinching never generates a click. Letterboxing is excluded from coordinate mapping.

Pointer moves are coalesced to one animation-frame update, zoom transforms update the DOM directly, and frames do not enter a shared store or React state. Repeated transport state notifications are deduplicated. A memo boundary isolates the open panel from unrelated homepage streaming renders. Resize, close, cancellation and transport changes clear pending gestures. Text entry and common navigation keys are available below the screen.

Mobile controls use gamepad-style translucent icon buttons at the lower corners instead of a persistent toolbar or expandable action menu: scroll mode and fit on the left, keyboard on the right. Buttons use the shared mobile glass style at 60% opacity (fully visible on hover, focus or selection). Text entry and navigation keys open in a floating panel above the buttons; it scrolls within short landscape/keyboard layouts without changing viewport geometry. Controls are siblings of the remote pointer surface so their touches never become native desktop input. Hiding the keyboard does not reconnect or change scroll mode. Transport names are not displayed in the operation UI.

## Validation and remaining platform gates

Focused tests cover message validation, real auth/origin gates, revocation, single ownership, delayed startup/abort, real Relay WS dispatch/fragmentation, runtime switching, decoded-frame ACK, coordinate mapping, pinch cancellation, and 50 unrelated homepage renders. The Electron evidence fixture runs the production capture page/preload with a synthetic canvas, a real Chromium WebRTC receiver and JPEG fallback; it does not capture or control the user's desktop. A separate local visual fixture was checked in Chromium at 390×844 and 844×390 using the production panel and synthetic screen data. That checks panel layout, not physical-phone rendering or real desktop capture.

Development-only native acceptance additionally exercised the production adapter and input helper against the real macOS desktop: JPEG frames decoded at 1440×810, and a fixed 26-character test string reached an isolated test textarea through Quartz input. The focused test window reported native/window/DOM keyboard focus. An earlier run received frames but not the text; that run did not measure focus and its cause is unresolved. This is not yet a repeatability guarantee. No real screen images or user-entered text were retained. The permission probe returned granted Screen Recording and Accessibility when Electron was started through macOS Launch Services; starting the same executable as a shell child reported denied/untrusted. Permission checks must be made under the actual launch context rather than inferred from the app's path or a Settings toggle.

Additional local checks confirmed new capture can start while the Mac remains locked (108 non-black JPEG frames), and the user reported the one-shot dummy password input test succeeded; no login was submitted. Transitioning an existing capture into lock still ended the session, and a later transition trace timed out awaiting local consent. These are distinct outcomes: locked capture/input is not evidence that lock/unlock transitions or correct-password unlocking are reliable.

The native setup adapter was also exercised via Launch Services with real app/helper permissions: it reported default-off, all required permissions granted, then enabled and disabled correctly using a test-only in-memory preference store. The production Settings group was visually checked at 900px and 350px widths using simulated native status; that does not prove release-signed IPC/permission onboarding. Focused tests cover disabled authenticated upgrades, native default-off, enable checks and failed writes, pending approval cancellation, active-session stop, local-only IPC classification, setup UI guidance and failed refresh preservation.

These tests do **not** prove macOS TCC permission inheritance for a release-signed helper, successful password-based unlocking, reliable lock/unlock transitions, iPhone WKWebView playback/gestures, WAN codec negotiation, throughput, battery or latency. Before shipping, verify those on a signed preview installer and a physical phone, including permission denial/regrant, display changes, disconnect while dragging, direct connection, Relay-only fallback and optional TURN. Native main/preload/helper changes require a new desktop installer; UI OTA alone cannot provide them.
