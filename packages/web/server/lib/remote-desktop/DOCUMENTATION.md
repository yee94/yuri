# Remote desktop

## Ownership and supported runtimes

- `runtime.js` owns the authenticated `/api/remote-desktop/ws` session and `/api/remote-desktop` capability response. The routes are installed before the OpenCode proxy/SPA fallback.
- Electron injects a process-local adapter from `packages/electron/remote-desktop.mjs`. Only that Electron Host's physical primary display is captured, irrespective of which OpenCode/runtime the desktop window currently shows.
- The first native input adapter is macOS (Quartz events, Screen Recording and Accessibility consent). CLI/headless, Windows and Linux Hosts return `supported: false`, and WS upgrade returns 501. VS Code explicitly returns 501 rather than proxying these routes to OpenCode.
- Hosted mobile and Capacitor iOS/Android use the same receiving browser UI. No native WebRTC plugin, new dependency, separate desktop server, or OpenCode changes are required.

## Authorization and lifetime

Remote desktop is opt-in. The native-only approval store also owns an `enabled` Boolean that defaults false when missing or malformed; pre-existing device approvals do not imply the feature is enabled. `/api/remote-desktop` exposes `{ supported, enabled }`, and WS upgrades are rejected with 403 while disabled, before starting native consent or capture. The native adapter checks the preference independently. Only local main-frame desktop IPC can inspect setup permissions, change the switch, or request a fixed macOS permission pane. There is no HTTP endpoint to enable it remotely.

The local desktop Settings → Remote instances → Remote desktop group checks Screen Recording, Accessibility for the app and the actual helper executable, and helper installation. The helper's check-only mode posts no input events. Enabling requires all checks to pass and a successful atomic preference write. Closing the switch immediately ends active and pending native sessions. Failed disable persistence leaves the current app run blocked rather than restoring remote access; a restart may still load the old persisted preference, so the failure is visible and must be retried. The existing serialized native store retains the enable preference; legacy device approval IDs are preserved but ignored. UI permission reads use Query, mutations refresh only their native setup/capability keys, stale runtime completions are rejected, and read failures preserve the last snapshot with explicit error feedback. Non-desktop and remote-runtime Settings cannot change local macOS grants. Unsupported desktop platforms show an unsupported state.

The WebSocket must authenticate a paired client or a real password-protected owner session. Password-less/forged owner cookies, loopback source, and raw bearer credentials in query parameters do not qualify. Browser sockets use the existing scoped `yuri_url_token`; the Host checks origin even when password auth is disabled. Both tunnel and URL-token allowlists include exactly `/api/remote-desktop/ws`. Desktop realtime proxying also permits this exact path. No Relay wire-frame types or crypto format change.

Once enabled locally and system permissions are granted, authenticated paired devices and password-authenticated owner sessions start directly without a per-connection confirmation, approval checkbox, or visible sharing-control window. Startup rechecks Screen Recording and app/helper Accessibility without requesting new permissions; revoked/missing grants fail closed and must be restored from local Settings. The only capture BrowserWindow is hidden and remains isolated. No Stop/Forget preload methods or IPC listeners remain. Close the remote view, disable the local setting, or revoke device pairing to stop control. Remote client revocation remains authoritative; no authentication or origin gate is bypassed. macOS-owned permission prompts and recording indicators are not hidden.

There is one active or pending capture per Host. Stopping the Host, disabling the feature, closing the remote view/socket, backgrounding the phone, removing/changing a display, or a native failure stops the session. Client pings are every 5 seconds; 20 seconds without a ping ends the Host session. Active client revocation is checked every 5 seconds, failing closed on store failure. Maximum session length is one hour. Initial client startup has a 60-second deadline, capability requests a 10-second deadline, and native capture readiness has a 15-second deadline.

Runtime generation/transport identity are captured when opening the view. No input or delayed auth result can connect to a different Host. Failure is not an empty success. Reconnection is explicit. Closing a pending session aborts startup; a later permission check or source-discovery completion is immediately disposed. EOF on the helper's pipe releases a held mouse button.

## Media and control

The isolated file-origin capture window uses Electron's `desktopCapturer` screen identity and Chromium's desktop `getUserMedia`, constrained to 2560×1440 and 30 fps so zoom can request more detail. Normal encoder output remains bounded by the ordinary adaptive tiers below. Chromium owns negotiated video codec and hardware acceleration; H.264 is not forced. A WebRTC offer/answer and trickle ICE pass over the authenticated WS. Media uses WebRTC DTLS-SRTP. Over Relay, the fingerprint-bearing signaling and control are also protected by the existing E2EE tunnel; media does not use Yuri's tunnel encryption format.

The capture renderer's `remote-desktop-quality.mjs` adds encoder ceilings alongside Chromium's own congestion control, with `degradationPreference: balanced`. Initial output is the 720p tier, not full quality. For a 1920×1080 capture, the tiers are:

| Output ceiling | FPS ceiling | Bitrate ceiling | 1080p reference divisor |
| --- | --- | --- | --- |
| 640×360 | 8 | 350 kbps | 3 |
| 960×540 | 12 | 750 kbps | 2 |
| 1280×720 (initial) | 20 | 1.5 Mbps | 1.5 |
| 1920×1080 | 30 | 3 Mbps | 1 |

Normal dimensions are bounded independently of source size while preserving its aspect ratio, with no upscaling of smaller captures. The reference divisor is multiplied by `max(sourceWidth / 1920, sourceHeight / 1080)` and clamped to at least 1: for a 2560×1440 source, the initial divisor is 2 and output is still 1280×720, not 960p. These are ceilings, not guaranteed throughput or bandwidth reservations. Every 2 seconds while connected, the renderer reads current video outbound stats and their linked remote RTP/selected ICE pair, ignoring unrelated streams/pairs. Two consecutive pressured samples step down one tier: bandwidth/CPU limitation, fresh loss ≥5%, selected-path capacity below 75% of the current ceiling, RTT >450ms, or RTT above 250ms and 150ms above its session minimum. Eight consecutive healthy samples step up one tier, requiring no limitation, loss <2% when present, RTT <250ms when present and estimated capacity ≥110% of the next tier when available. Without capacity estimates, fresh loss and RTT feedback are required for recovery. Missing, repeated and idle samples reset the streaks rather than proving spare bandwidth; stalled sends with explicit bandwidth/CPU limitation still count as pressure. Low bytes-per-second alone is never treated as congestion. Unsupported/failed stats or parameter calls retain the last working settings and retry without forcing JPEG fallback. Updates preserve encoding identity and sender transaction parameters; sampling never overlaps and stops on fallback/unload. No user-facing quality toggle is introduced.

### Zoom detail priority and mixed versions

Pinch or Drag double-tap zoom enters detail priority above 1.05× and leaves at or below 1.01× (hysteresis avoids near-Fit chatter). The panel sends only state transitions, not a message per movement/frame, and retains no extra React/server cache state. The session connection negotiates this through `ready.zoomQuality: true` before sending `{ type: 'view', zoomed: boolean }`; startup retains only the latest desired state. Runtime switching/close forbids late messages. Old/non-advertising Hosts receive no new message and keep existing local zoom. New Hosts with old clients default to ordinary adaptive quality.

The backend explicitly passes `zoomQuality: true` when starting a supporting adapter; the native adapter defaults this flag false and passes it into capture startup. Only a full supporting backend/native/capture path advertises support. This also covers a newer installer running an older OTA backend. The server ignores valid `view` controls if its native adapter did not advertise support; the parser accepts only a Boolean and projects away client-supplied bitrate/resolution values. Electron forwards the view control to capture, never to the Quartz input helper. Authentication/origin, session lifetime, rate/size limits and Relay framing remain unchanged.

While zoomed, all four WebRTC tiers use `scaleResolutionDownBy: 1` (up to the captured 1440p source) and `degradationPreference: maintain-resolution`. They keep the same adaptive bitrate ceilings but reduce FPS ceilings to 2 / 5 / 10 / 15 respectively, prioritizing text detail over motion instead of blindly raising bandwidth. Fit immediately restores the ordinary resolution/FPS of the current tier, not a new high-quality default. Chromium still owns actual congestion handling; this is a resolution preference, not a guarantee that a severely constrained network can deliver a sharp frame immediately. Parameter writes are serialized, latest zoom state wins over an in-flight update, and failed tuning is retried by the stats loop without disconnecting working video.

`YURI_REMOTE_DESKTOP_ICE_SERVERS` optionally supplies an RTCIceServer JSON array (maximum 8 entries). It is configured on the Desktop Host, not the Relay, and passed to both peers for that session. No external STUN service is contacted by default. Deployment-managed TURN credentials are visible to the paired receiving client as necessary for WebRTC and are never persisted or logged by this feature. Prefer short-lived credentials. A TURN credential minting service is not included.

If WebRTC fails, is unavailable, or produces no decoded video within 7 seconds of the answer, the client requests JPEG fallback through the existing runtime WS. This works over Relay without TURN. Fallback is at most 1440×900, JPEG quality 0.65, maximum 512 KiB per frame, and at most approximately 12 frames/second. Only one frame is outstanding: the receiver ACKs after image decode, and capture skips work until ACK. Thus effective frame rate also depends on RTT/encode/decode time; this is not a 30-fps WAN guarantee. WS buffering is capped at 512 KiB. The video fallback shares the connection with other Relay traffic.

Before sending JPEG, the capture page compares its complete encoded bytes with the previous sent frame, retaining at most one 512 KiB JPEG in memory for that session. Identical frames send nothing; any encoded change (including a small text edit) sends normally. This is exact comparison, not a low-resolution image/hash heuristic. Static-frame suppression saves network/Relay bytes, but the polling draw/encode work still occurs: it is not a capture-CPU optimization. A failed main-process `send()` returns a local-only `ack` with `dropped: true`, clearing duplicate history so an unchanged frame is retried instead of leaving the receiver stale. The wire ACK format, one-outstanding-frame bound and maximum frame size are unchanged. Teardown clears retained bytes and ignores late encoding completion. ACK-based JPEG quality/interval adaptation is not part of this change.

Zoomed JPEG raises its cap to 2560×1440 and quality to 0.8, with at most 4 capture cycles/second rather than the normal approximately 12 fps. Oversized frames retry at 0.5 then 0.25 JPEG quality while preserving resolution, and frames still over 512 KiB are skipped. Zoom/Fit invalidates duplicate history for a detail refresh, but never bypasses an outstanding decode ACK. An encode completed for an obsolete zoom state is discarded rather than sent stale. Fit restores 1440×900 / 0.65. These are bounded zoom profiles, not ACK-based adaptive JPEG quality.

The UI calls JPEG fallback “Compatibility stream”, not “Encrypted tunnel”: direct `ws://` transport is not E2EE. Use HTTPS/WSS for direct network connections and TLS for public Relay ingress. JPEG carried through Relay benefits from the existing endpoint-to-endpoint encrypted tunnel; a plain direct LAN connection does not acquire that property merely by using this feature.

Control always stays on the authenticated WS, including when video is P2P. `protocol.js` bounds and projects pointer coordinates, scroll deltas, text (1024 UTF-16 code units), key names, SDP (64 KiB), and ICE candidate fields. There is no arbitrary shell/keycode/file/clipboard API. WS messages are capped at 96 KiB; input is serialized with at most 32 queued commands and 150 messages/second. The native helper checks permission and active display again, and accepts only its own bounded JSON command vocabulary.

## Mobile interaction and performance

The Projects homepage plus menu ends with a Remote desktop icon/action after instance choices. The chat header overflow menu exposes the same action. `MobileApp` owns one open state and one shared entry handler; the homepage receives it through `MobilePhoneShell` and its Projects container. `RemoteDesktopPanel` now renders an opaque, viewport-filling standalone page in a body portal, not a sheet/dialog. It registers `remote-desktop-page` as its own root route with `useMobileBackRoute`, reusing the shared hosted-browser history and native Back coordinator. Back returns to the unchanged source tab/chat; it does not pop the retained chat route. The underlying shell is inert, the native dock is covered and the native composer uses the existing reference-counted cover. Root route gestures remain enabled for this page while underlying header navigation is blocked. Closing/unmounting releases the connection and native cover.

The page uses the current runtime, not a separately selected machine. It defaults to Drag mode: one finger pans the local canvas and never sends mouse/scroll input, including long presses. Cursor mode sends tap/double-tap clicks, held-mouse drags and long-press right-clicks. Switching modes cancels pending input/releases a held mouse without losing zoom/pan. Two fingers zoom (0.5–5× while held) and pan locally in either mode without sending mouse input. Releasing the last finger below 1× restores the fit transform; 1× means the fitted screen, not one remote pixel per CSS pixel. Switching from a remote drag to pinching releases the mouse; lifting one finger after pinching never generates a click. Letterboxing is excluded from coordinate mapping.

Drag follows image-preview semantics: two short taps within 300ms and 24 CSS pixels zoom to 2.5× around the tapped point (clamped to visible bounds); another double tap while zoomed restores Fit. Cursor double taps remain native clicks and never zoom locally. At 1×, Drag movement follows the finger but snaps back to the original fit position when released; the same applies below 1×. Zoomed panning remains in place. Fit and double-tap transitions use a short transform-only settlement, disabled for reduced motion; pointer/pinch movement is immediate. Cancelling/resetting clears double-tap candidates so a new mode or pinch cannot inherit a stray tap.

Pointer moves retain only the latest client coordinates per pointer. Each animation-frame flush reads viewport bounds once, converts both fingers using that same geometry, updates both pointer positions before calculating the pinch, and writes at most one transform. Pointer-move handlers perform no layout reads. Zoom transforms update the DOM directly, and frames do not enter a shared store or React state. Repeated transport state notifications are deduplicated. A memo boundary isolates the open page from unrelated homepage streaming renders. Resize, close, cancellation and transport changes clear pending gestures. Text entry and common navigation keys are available in the full-width keyboard footer.

Like image preview, the remote viewport also cancels cancelable native `touchmove` events using an explicitly non-passive listener. Android Chromium can otherwise begin native panning from stale compositor touch-action regions on transformed layers and cancel the pointer stream, even with `touch-none`. Pointer events remain the sole owner of local zoom and remote input; the touch listener performs no geometry reads, state updates or duplicate gesture processing. It is scoped to the viewport (not the keyboard/controls/document) and removed on unmount. Like image preview, the page tracks its own active pointer IDs instead of requiring `hasPointerCapture`, prevents default on tracked pointer moves, and does not treat `lostpointercapture` as a gesture cancel; only `pointercancel` cancels. Viewport and remote-size resets are skipped while a pointer is active, and viewport changes below 1 CSS pixel never reset zoom. Regression checks cover native-pan prevention, unaffected controls, listener cleanup, capture-less pinch continuation and resize during a pinch; physical Android WebView acceptance remains required.

Mobile controls use gamepad-style translucent icon buttons at the lower corners instead of a toolbar/menu: Drag and Cursor on the left, keyboard on the right. There is no scroll or Fit button. Floating Back and orientation controls sit at the top corners without a title bar. All five circular controls use shared `Button mobileGlass` + `mobileIcon`, consuming the existing liquid-glass fill, highlight, shadow, blur and saturation tokens without feature-local opacity or ring overrides. Selected modes and the open keyboard use the existing `yuri-mobile-inverse-action` tint while retaining the shared glass material. Text entry/navigation keys open in a full-width, in-flow footer below the canvas region; the canvas uses the remaining height rather than sitting behind the input. Navigation keys use shared sprite icons with accessible labels and tooltips, not text glyphs. The footer wraps key buttons on narrow widths and maps its padding to the page-local safe area. Controls are outside the remote pointer surface so their touches never become native desktop input. Hiding the keyboard does not reconnect or change modes. Transport names are not displayed.

`lib/remote-desktop/orientation.ts` and `useDesktopOrientation.ts` own page-local, manual-only orientation. The initial direction is captured once from the opening viewport; after that, only the orientation button changes the selected portrait/landscape direction and CSS rotation angle. ResizeObserver updates available dimensions only: neither a width/height swap nor keyboard open/close may choose, reverse or clear the angle. There is no device-orientation listener or sensor permission request, including on entry. Physical tilt cannot override the user's selection. This never changes native supported-orientation lists, calls a global orientation lock, or rotates the document/other routes. Locked-portrait native shells use a 90° transform on this page only, with swapped logical dimensions, inverse touch coordinates and remapped safe-area edges. Resize resets gesture geometry, not the network connection. The shared keyboard-inset surface keeps inputs accessible; opening it does not reinterpret IME height changes as physical rotation. Exiting removes resize/key listeners and page-local direction state. Native shell/global portrait restrictions are unchanged.

## Validation and remaining platform gates

Regression checks cover manual switching, ignored sensor events, no sensor permission requests/listeners, orientation cleanup on close, and a 120-event pinch burst plus 60 consecutive frames (one bounds read and transform write per flush, no React query work or native input). These deterministic operation-count checks do not establish physical iPhone frame times.

Focused tests cover message validation, real auth/origin gates, revocation, single ownership, delayed startup/abort, real Relay WS dispatch/fragmentation, runtime switching, decoded-frame ACK, coordinate mapping, pinch cancellation, and 50 unrelated homepage renders. The Electron evidence fixture runs the production capture page/preload with a synthetic canvas, a real Chromium WebRTC receiver and JPEG fallback; it does not capture or control the user's desktop. A separate local visual fixture was checked in Chromium at 390×844 and 844×390 using the production panel and synthetic screen data. That checks panel layout, not physical-phone rendering or real desktop capture.

Adaptive-media regression tests cover tier bounds/hysteresis, active-pair selection, stale/missing/idle feedback, rejected tuning, non-overlapping stats and fallback/unload cleanup. A 1000-frame duplicate burst sends only the first frame; one-byte changes remain observable. The real Electron evidence fixture stages the capture assets from the installer file list, loads their file-origin ES modules under CSP, sends a synthetic 1440p canvas through native WebRTC and applies controlled poor/healthy stats to verify real encoder downshift/recovery. It then freezes the canvas to verify zero repeated JPEG sends, changes a small patch and tests dropped-frame retry plus ACK gating. This is a controlled local feedback/encoding check, not evidence of weak-WAN latency, actual network estimation, release signing or physical-phone decode behavior.

Zoom checks additionally cover negotiated/missing support, old backend/native combinations, strict Boolean projection, direct/Relay view routing, no Quartz injection, zoomed bitrate preservation, serialized tuning, stale encodes and restoration to the current normal tier. Source-size tests keep the initial tier at 720p for 1440p, 1080p and 720p inputs. UI tests exercise double-tap/Fit and repeated pinch frames with only one detail transition, and confirm encoder-size changes do not reset local zoom. The real Electron receiver observes 2560×1440 WebRTC after zoom (at the initial 1.5 Mbps ceiling and 10 fps cap), returns to ordinary encoding on Fit, and decodes zoomed JPEG at 2560×1440 then normal JPEG at 1440×810. This synthetic-source run does not establish physical-phone zoom-to-sharp latency on a real weak network.

The standalone-page update was previously checked at both viewport sizes with a synthetic remote screen. Actual Chromium CDP touch dispatch verified inverse cursor coordinates, Drag double-tap zoom/restore and 1× pan snap-back. Real browser history Back unmounted the page and retained the source draft. Orientation is now manual-only; focused tests cover ignored sensor events, both inverse coordinate mappings, native back routing and no reconnection on direction/mode changes. Native dock/composer behavior and keyboard/safe areas on physical hardware remain device acceptance checks.

Development-only native acceptance additionally exercised the production adapter and input helper against the real macOS desktop: JPEG frames decoded at 1440×810, and a fixed 26-character test string reached an isolated test textarea through Quartz input. The focused test window reported native/window/DOM keyboard focus. An earlier run received frames but not the text; that run did not measure focus and its cause is unresolved. This is not yet a repeatability guarantee. No real screen images or user-entered text were retained. The permission probe returned granted Screen Recording and Accessibility when Electron was started through macOS Launch Services; starting the same executable as a shell child reported denied/untrusted. Permission checks must be made under the actual launch context rather than inferred from the app's path or a Settings toggle.

Additional local checks confirmed new capture can start while the Mac remains locked (108 non-black JPEG frames), and the user reported the one-shot dummy password input test succeeded; no login was submitted. Transitioning an existing capture into lock still ended the session, and a later transition trace timed out awaiting local consent. These are distinct outcomes: locked capture/input is not evidence that lock/unlock transitions or correct-password unlocking are reliable.

The native setup adapter was also exercised via Launch Services with real app/helper permissions: it reported default-off, all required permissions granted, then enabled and disabled correctly using a test-only in-memory preference store. The production Settings group was visually checked at 900px and 350px widths using simulated native status; that does not prove release-signed IPC/permission onboarding. Focused tests cover disabled authenticated upgrades, native default-off, enable checks and failed writes, pending startup cancellation, active-session stop, local-only IPC classification, setup UI guidance and failed refresh preservation.

After removing per-connection confirmation and the sharing window, a Launch Services probe enabled a test-only in-memory preference, started the production adapter directly, and decoded three real desktop JPEG frames at 1440×810 without saving images or sending input. The single capture window stayed invisible and not always-on-top, and shutdown left no windows. Synthetic tests additionally verify no confirmation dialog, no approval writes, no Stop/Forget IPC, permission-revocation failure, and cancellation during permission checking/source discovery. This does not verify release-signed behavior or physical-phone use.

These tests do **not** prove macOS TCC permission inheritance for a release-signed helper, successful password-based unlocking, reliable lock/unlock transitions, iPhone WKWebView playback/gestures, WAN codec negotiation, throughput, battery or latency. Before shipping, verify those on a signed preview installer and a physical phone, including permission denial/regrant, display changes, disconnect while dragging, direct connection, Relay-only fallback and optional TURN. Native main/preload/helper changes require a new desktop installer; UI OTA alone cannot provide them.
