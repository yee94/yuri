# Native lease / operation-owner contract

## Wire and fixed APIs

Native returns `{ connections, selected, runtimeScope: { hostID, lease } | null }` from `connection.list` and successful `connection.select`. The lease is Native-issued authority; JS never derives it from an id, epoch, timestamp or URL. `runtimeScopeFrom` accepts missing/null only for legacy read-only compatibility, rejects malformed non-null values and freezes a copy. A non-null snapshot scope must match its actual selection.

`bindRequest(scope)` and `bindRawRequest(scope)` capture one frozen copy. Both return `(path, method = 'GET', body?)`; every scoped GET also includes `expectedHost`. Every non-GET requires scope, including RPC reads implemented as POST. Raw preserves `{status, body}` even on HTTP errors for dedicated parsers. Ordinary `request` is **only** unbound GET compatibility; writes fail `scope_required` before Native. `native()` does not inject anything. Native must check expectedHost before dispatch and after suspension; JS factories do not grant a stale caller new credentials.

`app.runtimeScope` contains the adopted scope; `captureHostRequest()` is the factory for a newly created **operation owner**, not a function to call again after every await. Capture one sender and propagate it through compiler/materializer/helpers. Never replace an old continuation's sender with the current factory result.

`captureHostOperation()` is the small page-owner assembly interface: it returns a frozen `{ scope, generation, request, current }`. Construct it only after foreground snapshot confirmation, assign it as the replacement operation object, and capture that object at each action's entry. Its `current()` checks the admitted Host, origin, actual authorizationID, JS generation, lease and foreground/readiness; the page must additionally check its own lifetime/active state and `assignedOperation === capturedOperation`. An object created during the readiness gap remains invalid permanently. The request is fixed even when `current()` becomes false. This does not rebind any previously created Settings transaction/controller. Pure tests cover a foreground fixture repeating its old lease: the old operation still stays invalid because its generation changed, while a newly constructed one becomes current.

This operation object's `request` also checks its captured admission before dispatch and after response, rejecting `host_operation_stale` without dispatch when retired. Thus even a fixture that repeats its old lease cannot let the retired page operation write merely because a caller forgot the Host-generation check. The underlying sender remains bound to its old scope; no request is redirected to the replacement lane. Page disposal/route replacement still requires the owning page's token/active fence.

## Root lifecycle and Chat resumption

Native `setForeground(false)` synchronously retires its lease. JS root `runtimeLifecycle()` also clears its adopted scope/readiness, fences snapshot replies and retires operation authority. Foreground first reads a new `connection.list`; no global stream or Chat demand starts while that snapshot is pending. Snapshot read tickets fence older replies. Successful select directly adopts its returned snapshot without dropping it and doing a second list. Failed select re-reads actual Native authority; it cannot create a lease or clone the old connection merely to trigger a reconnect. Same-lease label/lastUsed metadata refresh updates only the metadata list and does not restart transport.

**Same-Host foreground is not an actual Host change.** Chat keeps its messages signal, loaded window/cursor, row references, draft/references/attachments, UI selections and mounted List owner. Only its operation lane is suspended. `chat.rebuildOperationLane()` explicitly creates a fresh lane after the root has confirmed a foreground snapshot for that same Host. `resumeChatOperations()` is the root fan-out seam for mounted suspended Chats; the existing root foreground acquisition calls it after snapshot adoption. Both return no-op for already rebuilt, disposed, or actually switched Hosts. The message-scope getter and lane revision advance, restarting the existing poll/stream owner without remounting Chat/NavStack. A verified legacy snapshot may rebuild a read-only lane; it cannot authorize writes, Goal POST or ASR.

Same-Host foreground also preserves `app.connection()` object identity; the replacement lease publishes through `app.runtimeScope`, not through a fake connection change. Explicit credential reconnect still rebinds its connection authority. Persistent Tabs must observe the confirmed runtime scope for operation rebuilding rather than depending on a connection-id or connection-object remount.

Each async Chat operation captures its lane/sender at entry and propagates it to nested helpers. Lane identity is checked in addition to Host epoch/lease, so an old read/prepare/ACK/finally cannot mutate the resumed lane, clear its flights, consume its draft or dispatch using its lease. Goal cancels read/command versions on suspension; single-request transport calls capture the explicitly rebuilt lane at admission. Materializer cancels queued work and captures the sender for each admitted read. The rebuilt operation lane receives a new lease/generation-scoped history/send gate. Closing the old gate releases only its history token; an old in-flight send release still releases only its original token. It cannot block or unlock the new gate. Unknown writes keep the existing durable journal and are never replayed by root/lane recovery.

Actual selection/credential rebind/Host change permanently retires the old Chat operation authority. A suspended Chat cannot be revived by A→B→A or by a later same-id lease. The appropriate existing navigation/Host-change owner decides what to display; this module does not remount UI or transfer old Host state into a different Host.

## Other persistent pages: explicit operation reconstruction, not page remount

The root/application owner may observe the adopted `app.runtimeScope` (or its existing Host epoch/page gate) to replace each page's operation object **after snapshot confirmation**. Keep the page's data, selection, navigation and UI signals; replace only its operation lane. Each lane owns its captured sender, active/current fence and in-flight slots. Retire that lane before assigning the replacement. Pass that sender to all child mutations and await continuations. Previously captured callbacks must check their original lane before writing local state. Scope-less legacy GET success is not evidence that a persistent mutation owner has been rebuilt. ASR and other Native operations need their own explicit scoped ownership; `native()` intentionally cannot fix them implicitly.

The root/navigation integration order is exact:

1. Keep the mounted `Route`, `NavStack`, `Chat`, List ref and row projector identities stable across foreground of the same Host. Do **not** key their lifetime on `epoch()`; it also advances for suspension, which is an operation fence rather than a navigation reset.
2. On background, retire each page's operation owner and its callbacks/tickets. Keep its rendered snapshot and local selections. `app.runtimeScope === null` never means that the selected Host changed or that its prior data is empty. Do not create a scoped mutation owner during this gap.
3. On foreground, wait for `loadConnections()` to adopt the actual Native snapshot. `runtimeLifecycle()` already does this and invokes `resumeChatOperations()` for eligible Chats. If main owns an additional explicit foreground path, call the same fan-out only **after** that awaited adoption; it is idempotent. Do not install a blanket scope-changing sender on existing async closures.
4. Compare the confirmed Host identity/origin with the mounted page's identity. Same Host: replace only each page's operation object from the new `app.runtimeScope`, capturing one request and one immutable lane token. Actual Host change: permanently retire the old operation owner and let existing Host navigation own the new contents. A→B→A is not a foreground resume.
5. Publish the new operation token/readiness to existing event handlers without remounting the persistent Home Tab or secondary page. Each user action captures that operation object before its first await. Its `current()` must check that exact object is still assigned, the actual page is active, the snapshot is confirmed and `sameRuntimeScope` still matches. A callback from an old object cannot call a new object's sender or any `chat.revert`/`chat.historyBusy.set`/draft setter.
6. In `application.tsx` specifically, the constructor `pageScope()` result and constructor `request = captureHostRequest()` cannot become foreground recovery automatically. The stable Chat UI lifetime needs a same-Host display gate, while transcript-history, speech/ASR, admission, metadata and other command/read owners need explicit replaceable operation gates. Cancel the old transcript-history owner **before** replacing its callbacks: its late `onPending(false)` must never release the new history gate. Rebuild those owners after confirmed scope using retained UI data; do not rerun an unknown admission/mutation to recover ownership. Context's `chat.messageScope` getter supplies the rebuilt scope; do not retain an old value as if it were still current.

This task did not modify application/business pages or Swift. Their owners must use this seam when replacing constructor-captured page operation owners; full-page/Chat/NavStack remount is not the recovery mechanism.

### Voice lifecycle red: concrete integration sites

The supplied production-engine log shows background `speech.stop/release` completing and foreground `connection.list`/root catalogs/stream succeeding, with no second `voiceRecognition.capabilities`. Current source explains the permanent gate: `settings-controls.tsx` captures `generation = epoch()` in `settingsLifetime`; `settings-basics.tsx` derives `voiceCurrent` from that fixed `state.current`, and its capability acquisition returns before calling Native when that predicate is false. `settings-basics.tsx` also aliases `state.request` and captures `expectedHost` at construction. `application.tsx`'s generic `pageScope()` separately freezes the same epoch.

The main/Settings owner needs an **explicit operation-only** rebuild after the confirmed snapshot. Keep the Settings Scroll, data/changes signals, edit revisions and Voice confirmation pending journal. Replace the Settings operation object using `captureHostOperation()`, and admit each `perform/load/confirm` with that captured object. A confirmation's GET after PUT must use the same captured object's sender; do not implement this by changing a request proxy or by updating the epoch variable read by old callbacks. The stable confirmation owner needs a lane-capture/replacement seam or retained-state reconstruction that keeps its pending acknowledgement/unknown-write journal; blindly disposing it loses that journal and is not equivalent.

After old tester/capture cleanup completes, build a new recognition adapter from the replacement object's exact `scope`, then reacquire capabilities and restore readiness. This is required even if a fixture repeats the same lease string, because the foreground operation generation is new. The existing `voiceTestVersion` can retire only the transient testing controller/session; it must not remount Settings editor/Scroll or replay Save/unknown writes. Root Host/route display gates must use stable mounted identity for same-Host foreground, with separate replaceable operation gates. This task establishes the state/factory contract and pure fences; the actual Settings integration and the main owner's single-engine rerun remain required and are not claimed passed here.

## Pure evidence and remaining acceptance

`runtime-scope.test.ts` covers strict parsing, immutable binding, scoped GET, raw responses, non-GET rejection and no implicit Native injection/replay. `runtime-scope-state.test.ts` uses a strict Native fixture: unknown operations throw, non-GET requires scope, and stale scopes reject. It covers A→B→A, foreground snapshot ordering, row/window/draft identity preservation, stale flights/prepare/ACK, no automatic unknown-write replay, metadata, failed select, old snapshots and legacy read-only mode.

These are JS/state contract tests, not Swift/setForeground, actual Host, Relay, UIKit, ASR or physical-device acceptance. Native validation and application/business operation-owner migrations require separate evidence from their owners.
