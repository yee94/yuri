## Implemented in preferences ownership

Follow-up now declares its existing appearance consumer. It still defaults to queue and retains both Host enum values. Existing Chat regression tests cover busy/idle, captured delivery, compilation failures, uncertain sends, restart and retry. No Chat or Goal source changed.

Before dispatching a preference PUT, the page persists a receipt through `settings-preferences-receipt` and the existing `openDraft` Storage/CAS lane. Network admission requires a successful durable write. The partition key includes the saved connection ID and authorization ID, excludes transient Host leases and URLs, and is shared by appearance/chat settings pages. Legacy connections without authorization identity cannot start a journaled Host write. Only an accepted transaction response marks the receipt acknowledged. If same-Host lease replacement causes the old operation/request fence to reject a late ACK after entering PUT, it remains unknown. GET equality is never an operation receipt and cannot certify or clear unknown. The settings route has no durable operation identity/deduplication or atomic rejection contract, so no entered-PUT response failure is treated as safe permission to replay. Save and Retry on a dispatched pending receipt send GET/application only, never the original Host PUT; a successful acknowledged recovery requires another explicit Save for later edits. Theme selection and mode PUTs use the same dispatch boundary.

The same owner separately proves a prepare attempt definitely unsent using an in-memory capability tied to the exact input object. prepare creates that capability before its Storage write; the page calls enterPut synchronously immediately before invoking the transaction, consuming the unsent proof. A prepare write failure or a lane retirement while awaiting prepare therefore has a safe cleanup path: cancelUnsent serializes a durable clear through the same CAS lane and only then clears the page's pending state. All submitted and newer edits remain dirty, and a separate explicit Save is required before any new PUT. Cleanup failure keeps the proof, receipt and dirty state, offers explicit Retry and blocks handoff/leave. It cannot be converted to an unknown handoff just to unblock navigation.

No preparing/unsent marker is persisted. A restarted or transferred owner has no capability to cancel a restored unknown record, enter/replay its PUT or certify it from a matching GET. Once enterPut has been called, cancelUnsent rejects; stale owners and stale same-value input objects also cannot cancel a newer attempt. Known-unsent cleanup is a local Storage operation and does not clear unrelated cache, drafts, credentials or Host state.

ACK alone never clears submitted values or dirty revisions. An acknowledged receipt must pass settingsPreferenceReadbackMatches against a fresh GET, then the existing appearance application and durable owner/CAS clear. The check compares each normalized submitted Host field: finite numbers follow the same client/server rounding, Boolean/enums keep exact types/values, and every submitted theme identity field must match with a consistent active palette. Missing values are not display defaults. Only three explicit Host semantics admit absence: an empty pwaAppName override is cleared, pwaOrientation=system and mobileKeyboardMode=native are Host formatter defaults. A display brand name is never persisted as the cleared override. Unknown receipts never enter this verification path; equal GET still cannot acknowledge them.

Filtered, differently applied or missing values retain the acknowledged receipt and original submitted dirty values, report settings.preferences.native.notApplied, and expose GET-only Retry. No Saved notice is published and PUT is never repeated. Receipt restoration repopulates absent submitted drafts at their original revisions while retaining/restamping newer unsent revisions, so close/reopen does not lose the original desired value or erase newer ABA input. After matching GET and successful appearance application, only unchanged submitted edit revisions clear; newer same-value ABA remains dirty. Local code/editor/keymap publications remain independently confirmed and are never included in Host verification or receipt patches.

ACK confirmation also supplies an exact operation/receipt/journal-current callback to refreshNativeAppearance. With a mounted root, createNativeAppearanceSync.refreshAfterCurrent captures that root's scope/generation, joins any already-running flight, checks the captured authority again, then uses the original refresh single-flight for a read initiated after the confirmation call. It rechecks authority after that refresh too. An old flight which already read fontSize=100 and delayed apply cannot satisfy a later ACK/GET=125 confirmation. Normal refresh, its Promise coalescing, pause/rebind and hold/resume semantics are unchanged; no second store or parallel settings reader is added. An absent root keeps its pre-existing no-op fixture contract. Fresh-read failure preserves the ACK receipt and submitted dirty values and permits GET-only retry, with no repeated PUT.

GET or native appearance failure keeps the acknowledged receipt; a resolved refresh promise with an appearance error signal is still failure. Pending receipts route Back/swipe through the guard, which performs a durable handoff before allowing navigation. Handoff increments its own durable transfer revision while preserving the exact original patch, submitted values, edit revisions, operation revision and acknowledged/unknown phase. Only after successful handoff does Back ask about newer unsent edits. Submitted values already protected by the receipt are not labelled as disposable unsent edits. Discard affects only those newer edits; it never clears a receipt. A failed Storage handoff leaves the page, receipt and edits intact and does not call onBack.

Unknown still has no terminal resolution protocol when its ACK was fenced out, and the UI states that it will not resend. This no longer traps the user on the page: close/reopen, other settings pages and process restart retain unknown with zero replayed PUTs. Acknowledged receipts can recover by GET/application and durable clear. The new receipt module reuses openDraft's real per-key serialized Storage/CAS and owner transfer, as features-receipt does; it does not create a parallel global data store. Its module-level map holds live owner tokens only and removes a token on close only if it still owns that identity. Persisted data has an allowlisted settings/theme patch and validated enum/number/edit revisions; no credentials or unrelated draft/cache data is admitted. features-receipt's route decoder remains restricted to Bot/plan paths and was not broadened.

Every asynchronous dispatch/recovery/handoff captures its receipt owner. Late operations from a disposed or superseded owner cannot confirm, clear or retire a newer owner. A retained covered navigation page explicitly reacquires the same authorized partition on activation; restore restamps its surviving unsent edits above the stored operation revision, preventing ABA loss. It never rebinds an old request to the new owner or Host lane.

Preferences publishes the existing `onCollectionNavigation` contract for dirty/busy/confirmation/pending-receipt/restoration states. Returning to the initial value removes an ordinary unsent draft entry; editing a still-pending field keeps its revision so recovery cannot erase newer input. Back is blocked during a local cache flight or Host write and checks its captured operation and journal owner around handoff/confirmation. The existing unknown message remains explicit; the ACK-not-applied message has translations in all ten locales. Discard labels only unsent edits, and a failed durable write uses the existing save-failed/changes-retained feedback.

Cache clearing captures `props.clearHistoryCache ?? state.clearHistoryCache` before confirmation. The production default is the original root singleton, never another cache or Host PUT. Confirmation and clearing have local busy flags included in navigation protection. Success/failure feedback belongs to the mounted page; Host lease changes neither cancel nor retry the local flight. Failure retains the cache owner's durable cleanup journal and exposes an explicit retry that confirms again. There is no automatic clearing loop. Page disposal suppresses late UI feedback without cancelling the singleton's ongoing cleanup. It does not clear drafts, pending queues, attachments, settings, credentials or live Chat authority.

### Device-local code and Skills editor font sizes

The Preferences number row reads `deviceAppearance()?.codeFontSize` directly. Unknown remains blank and disabled, including Reset; metadata's initial 100 is not a read fallback. Only the frozen singleton's successful empty Storage read supplies 100. Cold page reads and explicit read retries delegate to its existing loadDeviceAppearance; Preferences does not read/write Storage directly or construct another device store/root. The unique NativeAppearanceSync root still projects the published value into current.codeFontSize and the actual Chat/Thought/raw-tool/Diff consumers.

The code-size input stages dirty values. Save accepts only nonblank integers from 50 to 200, validates the applicable mixed Host patch before writes, and calls the original saveDeviceCodeFontSize singleton. Code size is explicitly excluded from settingsPreferencePatch, every Host PUT and the Host receipt. Known prior values and newer staged values survive failed reads or writes. Cold read failure has localized unavailable/reload feedback and an explicit read retry; failed writes retain the draft and retry Save. Successful local publication clears only that field's unchanged edit revision, including across Host lease renewal; a newer same-value ABA edit remains dirty. Successful local saves also clear prior local read/write feedback.

Save order is device code size, device editor size, existing device-Chat fields, then a new Host mutation or pending Host recovery. Device failure stops before starting a new Host write and preserves the remaining mixed draft. When local save succeeds but Host save/GET/apply fails, each local row reports its own confirmed save while the Host error/receipt remains visible. Save can commit new local font edits while a Host receipt is unknown or acknowledged-but-not-applied; that does not clear unknown or resend the Host PUT. A renewed lease cannot let the old mixed save dispatch its captured Host patch. Local write busy survives lane replacement for duplicate-save/back protection; each field has its own edit revision CAS, so a newer same-value ABA edit remains dirty. Hidden/disposed-page callbacks cannot edit/save either font field. Existing viewport visibility, renderer and receipt prepare/unknown logic are unchanged.

Editor size reads deviceAppearance.editorFontSize directly; unknown is blank and disables Input and Reset. A successful missing-record or legacy code-only record read supplies 13, never a failed/corrupt read. Nonblank finite drafts use Web's round then clamp to 9–32pt, with integer step 1; Reset stages 13 and only explicit Save persists it. Both fields live in the same device-appearance-v1 record and singleton serial lane: editor writes preserve code, code writes preserve editor, and read/write failures preserve the prior snapshot. Cold reads/retries use the existing loadDeviceAppearance port; no second root, store, per-editor Storage or GET was added. The Host sanitizer still excludes editorFontSize; local-only saves make zero Host PUTs, and local values never enter the Host mutation receipt.

Metadata declares only skills-editor consumption for editorFontSize. The two existing editable Skills inputs (instructions and supporting-file content) use nativeEditorTextStyle through SettingsInput.inputStyle, changing fontSize and lineHeight=1.5×pt on the same Input. Mono family follows canonical appearance; codeFontSize percentage, UI size and density do not rescale editor points. Read-only Skills TextViews remain code consumers. DedicatedMobile's actual MobileFilesSurface is read-only preview, with no CodeMirror, Vim or file-write entrypoint: a desktop FilesEditor/Vim implementation is not a mobile parity requirement. Production-prop callback tests preserve input value/onChange and construct one Input only; UIKit focus/selection/IME behavior still requires the main owner's engine/device validation.
